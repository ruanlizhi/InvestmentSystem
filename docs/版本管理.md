# 版本管理规则

## 两个仓库，一套软件

- InvestmentSystem：公开，MIT 许可；保存共用代码、通用文档、虚构测试和已批准的公开内容。
- InvestmentSystem-private：私有；保存真实记录、研究、个人方案和备份，不适用公开仓库的 MIT 授权。
- 软件只在公开代码仓库维护一份，两版使用同一构建。私人仓库不复制软件代码，也不通过公开仓库的分支保存私人数据。
- GitHub 保存源代码与版本历史，不等于网站已部署到互联网。

## 三种版本分开

| 对象 | 标识 | 何时更新 |
|---|---|---|
| 软件 | package.json 的版本号 + Git 标签 | 形成一批可交付改动时 |
| 代码修改 | Git commit | 每次完成一个可说明、可验证的改动时 |
| 投资数据 | revision 与每条记录 version | 数据保存入口提交修订时 |

私人日记、持仓和想法变化不要求升级软件版本；公开快照编辑通过代码仓库提交留痕，不自动读取未来私人内容。

## 软件版本号

采用 主版本.次版本.修订版本。本项目规则如下：

- 0.1.0：首个 Git 基线，属于早期预览；真实浏览器验收仍未完成。
- 0.1.1：修复问题、调整样式或公开文案，保持数据和接口兼容。
- 0.2.0：增加可独立说明的功能；0.x 阶段如存在不兼容改动，也提升次版本并明确迁移要求。
- 1.0.0：核心流程和验收闭环稳定后再决定，不因提交次数自动升级。
- 1.x 之后，破坏已承诺接口或数据兼容性的修改提升主版本，例如 2.0.0。

未交付改动记录在 CHANGELOG.md 的 Unreleased。交付时更新 package.json、变更日志并建立相同版本的标签 vX.Y.Z；已推送标签不移动、不覆盖。发现问题用新版本修正。

## 提交与发布

- main 保持可构建。较大功能使用 feat/名称 或 fix/名称 分支；小改动通过验证后可直接提交。
- 提交说明使用 feat:、fix:、docs:、style:、test:、chore: 等前缀，写明实际变化。
- 提交前检查 diff 和暂存文件；不把凭据、运行锁、缓存、依赖目录或未授权资料加入仓库。
- 发布前运行 bun test、bun run typecheck、bun run build、bun run check:release。
- UI 修改额外核验真实浏览器；未完成时必须在版本说明写明，不能把自动测试当作视觉验收。
- 数据格式变更单独提高 schemaVersion，并配备份、迁移和恢复验证。当前仅支持 schemaVersion 1，不自动迁移。
- 回退代码使用 revert 形成新提交，不重写已发布历史；数据恢复使用应用的备份恢复入口，不随意 git checkout 覆盖运行中的 state.json。
- 本次授权建立并上传两个仓库；以后未被要求上传时，不因本文件自动推送。

## 私人仓库

同步真实资料前核对远端所有者和 PRIVATE 可见性；只推送到指定私人仓库。runtime/state.json 及应用备份纳入私人版本管理，运行锁和临时写入文件忽略。修改数据优先走应用保存接口，Git 用于额外备份与追踪，不替代应用修订校验。
